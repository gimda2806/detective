# 충돌 감시 루틴

두 개의 Claude 세션이 같은 저장소를 동시에 고치고 있고, 그와 별도로 사건 생성 루틴이 주기적으로 새 마스터를 커밋·PR·머지한다. 이 문서는 그 셋이 서로를 밟는 것을 찾아내는 감시 루틴의 지침이다.

**이 루틴은 아무것도 고치지 않는다.** 찾아서 적기만 한다. 고치는 것은 해당 작업을 하던 세션의 몫이다.

## 왜 git만으로는 부족한가

실제로 일어난 충돌을 분류하면 넷인데, git이 잡아 주는 것은 첫째뿐이다.

1. **브랜치가 낡아서 나는 머지 충돌.** git이 잡는다. 다만 머지를 눌러 봐야 안다 — 미리 알면 한 번의 헛된 시도를 아낀다.
2. **git이 조용한 의미 충돌.** 한쪽이 지운 파일을 다른 쪽이 여전히 참조한다. 텍스트로는 겹치지 않아 양쪽 다 "깨끗하게" 머지되고, 합쳐진 결과만 깨진다. `data/cases/CASE014/case.json`을 한 세션이 지웠는데 다른 세션의 `mockGm`이 옛 CASE014 인물(`백지훈`/`임채원`)을 그대로 하드코딩하고 있던 것이 이 경우다.
3. **같은 파일의 다른 층.** `app/game.ts`는 10,000줄이 넘어서 두 세션이 서로 다른 함수를 고치면 git은 깨끗하게 합친다. 그런데 한쪽이 `getCase()`를 동기 맵 조회에서 비동기 에셋 페치로 바꾸면, 다른 쪽의 호출부는 문법적으로 멀쩡한 채 의미가 깨진다.
4. **사건 번호 충돌.** `npm run next:case-id`가 고르는 번호와 손으로 적은 번호가 같은 자리를 잡는 경우.

그러니 감시의 값어치는 **2·3·4**에 있다. 1은 덤이다.

## 범위 — 무엇을 보지 않는가

- 원격 브랜치가 213개, 열린 PR 중 여러 건이 몇 주째 멈춰 있다. **최근 24시간 안에 갱신된 것만** 본다. 멈춘 것은 충돌이 아니라 방치다.
- `data/pending-cases/` 아래 마스터 내용 자체는 보지 않는다. 그건 `npm run check:case`의 일이다.
- 코드 품질·설계 의견은 적지 않는다. 충돌만 적는다.

## 검사 항목

매 실행에서 아래 다섯을 순서대로 본다. 각 항목은 **구체적인 파일·심볼·PR 번호**까지 적어야 한다 — "겹칠 수 있음" 같은 문장은 받는 세션이 아무것도 할 수 없으므로 적지 않느니만 못하다.

### A. 지워졌는데 아직 참조되는 것

최근 24시간 동안 main에서 삭제된 파일을 모은 뒤(`git log --diff-filter=D --name-only`), 그 경로와 그 파일에만 있던 고유 식별자(사건 ID, 인물 이름, 내보낸 심볼)를 저장소 전체와 최근 갱신된 열린 PR의 diff에서 찾는다. 하나라도 걸리면 그게 가장 중요한 발견이다.

### B. 같은 파일을 두 곳에서

최근 갱신된 열린 PR들의 변경 파일 목록을 모아, **둘 이상의 PR이 건드리는 파일**과 **PR이 건드리는데 그 PR의 base 이후 main에서도 바뀐 파일**을 찾는다. 다음은 겹치면 항상 적는다:

- `app/game.ts`, `app/gm/*.ts`
- `app/DetectiveApp.tsx`, `app/CaseLibrary.tsx`, `app/globals.css`
- `vite.config.ts`, `package.json`, `scripts/build-case-assets.ts`

### C. 시그니처가 움직인 내보낸 심볼

최근 24시간 main 커밋에서 `app/game.ts`·`app/gm/*.ts`의 함수 선언 줄이 바뀐 것을 추린다(동기 → `async`, 매개변수 증감, 반환 타입 변경). 그런 심볼이 있으면 최근 갱신된 열린 PR에서 그 심볼의 호출부를 찾아 함께 적는다. **동기가 비동기로 바뀐 것이 가장 위험하다** — 호출부가 `await` 없이도 컴파일되는 경우가 있다.

### D. 사건 번호 충돌

열린 PR 중 `data/pending-cases/CASEnnn/`을 추가하는 것들의 번호를 모아, 서로 겹치거나 이미 main에 있는 번호를 쓰는 것을 찾는다. `case_registry.json`에 있는 번호는 폴더가 없어도 쓰인 번호다.

### E. 머지 가능 여부

최근 갱신된 열린 PR의 `mergeable_state`를 확인한다. `dirty`면 base를 들여와 풀어야 한다고 적는다.

## 보고 — 하나의 이슈를 갱신한다

제목이 정확히 **`충돌 감시: 열린 항목`** 인 이슈 하나를 쓴다.

- 그 이슈가 없고 이번에 발견한 것이 있으면 **새로 연다.**
- 있으면 **본문을 이번 결과로 통째로 갈아 끼운다.** 새 댓글을 달지 않는다 — 매시간 도는 루틴이 댓글을 쌓으면 하루에 24개가 된다.
- 발견한 것이 하나도 없으면 **그 이슈를 닫는다.** 없으면 아무것도 하지 않는다.
- 특정 PR 하나에만 해당하는 발견(B·D·E)은 그 PR에도 댓글을 **한 번만** 단다. 이미 같은 내용의 댓글이 있으면 다시 달지 않는다.

본문 형식은 매번 같아야 한다. 다음 실행이 무엇이 새로 생겼는지 눈으로 바로 알 수 있어야 하기 때문이다:

```markdown
마지막 검사: <UTC 시각> · main: <짧은 SHA>

## 지워졌는데 아직 참조됨
- `<경로>` (main <SHA>에서 삭제) ← `<참조하는 파일>:<줄>`이 아직 `<식별자>`를 쓴다

## 같은 파일을 두 곳에서
- `app/game.ts` — PR #A(`<브랜치>`), PR #B(`<브랜치>`), main <SHA>

## 시그니처 변경
- `getCase()` 동기 → async (main <SHA>) ← PR #A `<파일>:<줄>`

## 사건 번호 충돌
- CASE123 — PR #A, PR #B

## 머지 불가
- PR #A (`dirty`) — base를 들여와야 한다
```

빈 항목은 아예 적지 않는다.

## 하지 말 것

- **코드를 고치거나 푸시하지 않는다.** 충돌 해소는 그 작업을 하던 세션이 맥락을 쥐고 해야 한다.
- **PR을 머지하거나 닫지 않는다.**
- **24시간 넘게 멈춘 PR에 댓글을 달지 않는다.** 그건 충돌이 아니다.
- **발견이 없으면 아무 글도 쓰지 않는다.** 조용한 실행이 정상이다.
