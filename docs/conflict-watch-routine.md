# 충돌 감시 루틴

두 개의 Claude 세션이 같은 저장소를 동시에 고치고, 그와 별도로 사건 생성 루틴이 주기적으로 새 마스터를 커밋·PR·머지한다.

**이 루틴은 아무것도 고치지 않는다.** 찾아서 적기만 한다. 고치는 것은 그 작업을 하던 세션의 몫이다 — 맥락 없이 남의 충돌을 푸는 것이 충돌 자체보다 위험하다.

## 왜 이것만 남았나

"공유 파일을 건드리기 전에 서로 알린다" 같은 약속은 사람이 전달책이 되어야 해서 지속되지 않는다. 그래서 기계가 할 수 있는 것은 전부 기계로 내렸다:

- **PR 검사**(`.github/workflows/pr-checks.yml`)가 `tsc --noEmit` · oxlint 기준선 · `npm run build` · 바뀐 마스터의 `check:case`를 돌린다. 시그니처 드리프트는 여기서 죽는다 — main에서 `getCase()`가 동기에서 비동기로 바뀌었는데 다른 브랜치의 호출부가 그대로면, **깨뜨린 PR이 스스로 빨개진다.** 아무도 알릴 필요가 없다.

이 루틴에 남는 것은 **PR 검사가 구조적으로 볼 수 없는 둘**뿐이다.

1. **컴파일이 통과하는 의미 충돌.** 한쪽이 지운 것을 다른 쪽이 문자열로 물고 있는 경우. 텍스트 충돌도 타입 오류도 없이 합쳐지고 결과만 어긋난다. `data/cases/CASE014/case.json`이 삭제됐는데 `app/game.ts`의 `mockGm`이 옛 CASE014 인물(`백지훈`/`임채원`)을 하드코딩한 채 남아 있던 것이 이 경우다. `tsc`는 여기에 대해 아무 말도 하지 않는다.
2. **열린 PR끼리의 충돌.** PR 검사는 자기 PR만 본다. 열린 PR 둘이 같은 파일을 고치거나 같은 사건 번호를 잡는 것은 어느 쪽 CI도 모른다.

## 범위 — 무엇을 보지 않는가

- 원격 브랜치가 200개가 넘고 열린 PR 여럿이 몇 주째 멈춰 있다. **최근 24시간 안에 갱신된 것만** 본다. 멈춘 것은 충돌이 아니라 방치다.
- **PR 검사가 이미 보는 것은 보지 않는다** — 타입 오류, 빌드 실패, 린트, 마스터 검증. 빨간 PR은 그 PR의 주인이 본다.
- 마스터 내용 자체는 보지 않는다. 그건 `npm run check:case`의 일이다.
- 코드 품질·설계 의견은 적지 않는다.

## 검사 항목

### A. 지워졌는데 아직 참조되는 것 — 가장 중요하다

최근 24시간 동안 main에서 삭제·이름변경된 파일을 모은다(`git log --diff-filter=DR --name-only`). 각각에 대해:

1. 경로 문자열 자체를 저장소 전체에서 찾는다.
2. 그 파일에만 있던 **고유 식별자**를 찾는다 — 사건 ID, 인물 이름, 내보낸 심볼. 삭제된 사건 마스터라면 삭제 직전 버전(`git show <SHA>^:<경로>`)에서 `characters[].name`과 `case_id`를 뽑아 코드(`app/`, `scripts/`)에서 문자열로 검색한다.

`tsc`가 잡을 수 있는 것(사라진 심볼의 import)은 PR 검사가 이미 잡으므로 적지 않는다. **문자열로만 물려 있는 것**이 이 항목의 전부다.

### B. 열린 PR끼리 겹치는 것

최근 갱신된 열린 PR들의 변경 파일 목록을 모아 **둘 이상의 PR이 건드리는 파일**을 찾는다. 다음은 겹치면 항상 적는다:

- `app/game.ts`, `app/gm/*.ts`
- `app/DetectiveApp.tsx`, `app/CaseLibrary.tsx`, `app/globals.css`
- `vite.config.ts`, `package.json`, `scripts/build-case-assets.ts`

같은 파일이라도 **어느 함수·어느 절을 고치는지**까지 적는다. `app/game.ts`는 10,000줄이 넘어서 "겹친다"만으로는 아무것도 알 수 없다.

### C. 사건 번호 충돌

열린 PR 중 `data/pending-cases/CASEnnn/`을 추가하는 것들의 번호를 모아, 서로 겹치거나 이미 main에 있는 번호를 쓰는 것을 찾는다. `case_registry.json`에 있는 번호는 폴더가 없어도 이미 쓰인 번호다.

### D. 머지 불가

최근 갱신된 열린 PR의 `mergeable_state`가 `dirty`인 것. base를 들여와야 한다고만 적는다.

## 보고 — 하나의 이슈를 갱신한다

제목이 정확히 **`충돌 감시: 열린 항목`** 인 이슈 하나를 쓴다.

- 없고 발견한 것이 있으면 **새로 연다.**
- 있으면 **본문을 이번 결과로 통째로 갈아 끼운다.** 새 댓글을 달지 않는다 — 매시간 도는 루틴이 댓글을 쌓으면 하루에 24개가 된다.
- 발견이 하나도 없으면 그 이슈를 **닫는다.** 없으면 아무것도 하지 않는다.
- PR 하나에만 해당하는 발견(B·C·D)은 그 PR에도 댓글을 **한 번만** 단다. 같은 내용의 댓글이 이미 있으면 다시 달지 않는다.

본문 형식은 매번 같아야 한다. 다음 실행이 무엇이 새로 생겼는지 눈으로 바로 알 수 있어야 하기 때문이다:

```markdown
마지막 검사: <UTC 시각> · main: <짧은 SHA>

## 지워졌는데 아직 참조됨
- `<경로>` (main <SHA>에서 삭제) ← `<참조하는 파일>:<줄>`이 아직 `<식별자>`를 문자열로 쓴다

## 열린 PR끼리 겹침
- `app/game.ts` — PR #A(`<브랜치>`, `<함수>`), PR #B(`<브랜치>`, `<함수>`)

## 사건 번호 충돌
- CASE123 — PR #A, PR #B

## 머지 불가
- PR #A (`dirty`) — base를 들여와야 한다
```

빈 항목은 아예 적지 않는다.

## 하지 말 것

- **코드를 고치거나 푸시하지 않는다.**
- **PR을 머지하거나 닫지 않는다.**
- **24시간 넘게 멈춘 PR에 댓글을 달지 않는다.**
- **PR 검사가 이미 빨갛게 만든 것을 다시 적지 않는다.**
- **발견이 없으면 아무 글도 쓰지 않는다.** 조용한 실행이 정상이다.
