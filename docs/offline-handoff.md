## 한 줄 요약

같은 사건 데이터로 **OpenAI 호출 없이 돌아가는 게임**을 `/offline` 경로에 따로
올렸다. main의 AI판은 그대로 살아 있고, 화면에서 버튼으로 오간다.

## 지금 상태

- **`app/offline/`은 main에 머지돼 있다**(2026-09-17 확인). 이 문서 앞머리의
  「1차 배포 계획」은 그 전에 쓴 것이다.
- 전 사건 완주 검사 **311/311 통과**, 텍스트 이상 0건.
- `tsc --noEmit`, `oxfmt --check`, `oxlint` 모두 통과(신규·수정 파일 기준).

## 설계 원칙: 메인을 해치지 않는다

main과 **공유하는 파일은 3개뿐**이고, 나머지는 전부 오프라인 전용 신규 파일이다.

| | 파일 | 무엇이 바뀌었나 |
|---|---|---|
| 공유 | `app/game.ts` | `GameVariant = 'ai' \| 'offline'` 타입, `saveRowId()`/`casePath()`, 그리고 `saveState`/`loadState`/`stateView`/`listCases`/`resetGame`/`exportPlayLog`/`submitMessage`에 **`variant` 인자 추가(전부 기본값 `'ai'`)**. 기존 호출부는 한 줄도 안 고쳤다. |
| 공유 | `app/CaseLibrary.tsx` | `variant` prop 하나. 목록 화면을 양쪽이 같이 쓴다(따로 만들었다가 갈라져서 합쳤다). GM 전환 알약이 그 값으로 방향만 바꾼다. |
| 공유 | `app/globals.css` | **없음.** 한때 `.gm-switch*`를 넣었다가 알약으로 되돌리면서 main 쪽을 그대로 받았다. |
| 전용 | `app/gm/offline-engine.ts` | 규칙 기반 GM 본체(메뉴 생성 + 행동 실행 + 대사 풀). |
| 전용 | `app/gm/offline-session.ts` | 한 턴 조립(한지우 쿨다운, dialogue 배열). |
| 전용 | `app/gm/offline-summon.ts` | "한지우를 보내 부르기"의 상태 마커. |
| 전용 | `app/offline/*` | 라우트 2개, 서버 액션, 화면(`OfflineDetectiveApp.tsx`), CSS. |

**세이브도 분리돼 있다.** 같은 사건이라도 AI판은 `<caseId>`, 오프라인은
`<caseId>::offline` 행에 저장되므로 서로 진행을 덮어쓰지 않는다(`saveRowId()`).

## 어떻게 노는가

- `/offline` — 사건 목록. 상단 탭으로 AI판과 왕복.
- `/offline/<caseId>` — 플레이 화면.
- **대화창은 채팅이 아니라 한 편의 추리소설이다.** 도입부도 그 안에 있다. 아래 「장면 로그」 참고.
- **자유 입력이 없다.** 모든 행동이 버튼이다.
  - **현장·면담·인물·사건**은 가운데 행동 목록에서 고른다.
  - **이동**은 수첩의 `장소` 탭에서 장소 카드를 눌러서 한다.
  - **증거 제시**는 수첩의 `증거` 탭에서 카드를 여러 장 슬롯에 담고 `제시` 버튼.
- 장소 카드에는 접근 등급, `방문 N회`/`미방문`, `있는 사람`이 같이 표시된다.
- 상단의 표 아이콘이 **스프레드시트 위장 테마**. PC 전용이고, 저장 키
  (`detective:theme`)를 AI 화면과 공유하므로 한쪽에서 켜면 양쪽 다 켜진다.
- **인물은 Master가 정한 `present_location`에만 있다.** 예외는 하나 —
  이미 면담한 사람 한 명을 `한지우를 보내 ○○을 불러온다`로 데려올 수 있고,
  두 번째를 부르면 앞사람은 제자리로 돌아간다(한지우가 한 명이니까).

## 장면 로그 (2026-09-17, 2026-09-18 보강)

AI 화면의 말풍선은 **주고받는 대화**를 그리려고 만들어진 것이다. 플레이어가 한
마디 쓰고 GM이 한 마디 답하니 카드가 번갈아 놓이는 게 맞았다. 오프라인에는 그
왕복이 없다 — 한 턴이 언제나 [고른 행동] → [서술] → [탐정] → [한지우] 로 흐르는
한 방향인데, 그걸 카드 네 장으로 끊어 놓으니 테두리·그림자·아바타·14px 간격이
매번 네 번 끼어들었다. 특히 두 사람이 같은 턴에 주고받는 자리에서 두 줄이 서로
다른 카드에 갇혀, **받아치는 말이 받아치는 것으로 안 읽혔다**(사용자 지적:
「대사 중간중간 툭툭 끊겨」).

그래서 대화창을 대본 한 토막처럼 이어 읽히게 바꿨다. 카드가 하던 구분은
**간격이 대신한다**:

| 자리 | 간격 | 뜻 |
|---|---|---|
| 턴과 턴 사이 | 30px + 구분선 | 여기서 장면이 바뀐다 |
| 서술 → 첫 대사 | 15px | 같은 턴 안이다 |
| 대사 → 대사 | 3px | **이 둘은 서로에게 하는 말이다** |

- **고른 행동**은 초록 말풍선이 아니라 왼쪽에 작게 놓인 슬러그 라인 + 선이다.
  플레이어가 누른 버튼 이름이지 대화의 한 마디가 아니다.
- **탐정·한지우**는 이름을 왼쪽 62px 여백에 세우고 본문을 내어쓴다. 아바타는
  없앴다 — 동그라미가 매달려 있으면 그것만으로 줄이 따로 논다.
- **서술 속 큰따옴표**(그 자리 사람이 실제로 한 말)는 서술과 같은 왼쪽 끝에서
  시작한다. 한때 탐정·한지우와 같은 기둥에 들여 세웠지만 되돌렸다 — 소설에서
  대사는 문단 하나일 뿐 따로 들여쓴 칸에 들어가지 않고, 13px 로 내린 뒤에는
  그 빈 칸이 본문 폭을 더 좁혔다. 구분은 색과 굵기가 맡는다.
- **문장 단위 분리를 껐다.** `MessageContent`가 마침표마다 줄을 갈라 10px씩
  벌려 놓던 것 — AI 화면은 모델이 뱉은 긴 한 덩어리를 읽히게 하려고 그랬지만,
  오프라인 서술은 엔진이 이미 문단(`\n\n`)으로 끊어서 준다. 거기서 또 갈라
  놓으면 서술부터 이미 끊긴 채로 시작한다.
- 메모장 저장 단추는 짚은 줄에서만 뜬다(이미 담은 줄은 계속).

### 도입부도 이 안에 있다 (2026-09-18)

「사건의 시작」이 접히는 패널로 대화창 위에 따로 서 있었다. 같은 산문인데
**출력 형태가 둘로 갈려 있었다** — 도입부는 13px 에 대사가 인라인 초록
굵은 글씨(`.intro-dialogue`), 종결은 16px 에 대사가 62px 들여쓴 제 줄.
게다가 도입부는 `max-height: 38vh` 로 **자기 스크롤막대를 따로** 갖고 있어서,
한 사건을 처음부터 끝까지 한 편으로 읽는다는 것이 성립하지 않았다
(사용자 결정: 「시작부터 엔딩까지 한 사건을 이야기로 본 추리소설의 형태로」).

지금은 도입부가 `.messages` 안의 첫 블록이다. 「사건의 시작」은 행동 표지와
똑같이 생긴 슬러그 라인(`.message.scene-slug`)이 되고, 본문은 종결 장면과
같은 `MessageContent` 를 탄다. 도입부 → 수사 → 종결이 한 흐름, 한 활자다.

- **`public_intro` 를 직접 그린다.** `recent_conversation` 은 창이라 도입부가
  곧 밖으로 밀려난다. 창 안에 아직 남아 있는 동안은 `displayedConversation`
  이 그 첫 줄을 걸러내므로(기존 `originalIntro` 비교) 겹치지 않는다.
- **한 턴도 안 둔 상태에서는 맨 아래로 스크롤하지 않는다.** 도입부가 들어오면서
  첫 화면의 맨 아래가 「가장 최근 턴」이 아니라 「도입부의 마지막 문단」이
  됐다 — 그대로 두면 사건을 처음 여는 사람이 이야기의 첫 줄을 건너뛴 자리에서
  시작한다(고치기 전 CASE030 에서 `scrollTop` 745). 한 턴이라도 두면 종전대로다.
- **포맷 경고**(`format_warnings`)는 대화창 위로 올라왔다. 이야기가 아니라
  작성자에게 하는 말이라 스크롤 안이 아니라 위에 붙어 있어야 맞다.
- **접히는 패널은 스프레드시트 위장에만 남는다.** 그쪽은 한 줄이 한 행인
  표라 「이야기」가 성립하지 않고, 위장 테마가 `.case-brief` 를 표 머리말
  행으로 만드는 규칙을 이미 갖고 있다. `CaseIntroContent` 와
  `.case-brief*` CSS 는 그래서 지우지 않았다 — 위장 전용이 된 것이다.

### 전자책 활자 (2026-09-18)

두 번 손봤다. 처음엔 16px 그대로 두고 간격만 조였는데(「한 문단이 한 번에 안
보임」), 그래도 크다는 지적이 다시 왔다 — **「전의 사건의 시작 포맷이 더 나은
듯, 전자책 같은 느낌으로」**(사용자 결정). 16px 본문은 화면에 띄운 대본이지
읽는 책이 아니었다. 옛 도입부가 쓰던 13px 로 내렸다.

같은 오프닝 한 장: **855px → 646px.** 한 화면에 들어온다.

| | 값 |
|---|---|
| 본문 활자 | 13px |
| 줄높이(서술·대사 모두) | 1.75 |
| 단 폭 | 620px, 가운데 정렬 |
| 서술 색 | `#4e4b46` |
| 문단 사이 | 5px (`structured-message` gap 0 + `message-break` 5) |

**활자를 줄이면 단 폭도 같이 줄인다.** 13px 에 700px 폭이면 한 줄이 50자를
넘어가 눈이 줄을 잃는다. 620px 이 대략 40자다. 후보 넷 중 둘(14.5px 인데 폭만
좁힌 것)이 글자를 줄였는데도 **오히려 더 길어진** 것이 이 때문이다 — 882px,
898px. 줄바꿈이 늘면 활자를 줄인 보람이 사라진다.

**단은 가운데 선다.** 왼쪽에 붙어 있으면 넓은 화면에서 오른쪽이 통째로 비어
「왼쪽 칼럼」으로 보이고, 가운데 서면 그 순간 책의 한 쪽이 된다.

**간격의 순서를 뒤집지 말 것.** 대사↔대사 2 < 문단 사이 5 < 행동→서술 8 <
서술→대사 11 < 턴 사이 22. 그 순서가 무엇이 한 덩어리인지를 말한다. 더 조일
일이 생겨도 값만 내리고 순서는 그대로 둔다 — 특히 **대사와 대사 사이**는
언제나 제일 좁다. 장면 로그를 만든 이유가 그 자리다.

### 본문 서체 — 명조 (2026-09-18)

「전체적으로 추리소설을 보는 전자책 느낌이면 좋겠다」(사용자 결정)의 마지막
한 칸. 이야기 본문만 **Noto Serif CJK KR Regular** 서브셋으로 그린다.
자세한 것은 `public/fonts/README.md` — 여기서는 판단만 남긴다.

- **세리프는 본문에만.** 서술·서술 속 대사·탐정·한지우의 대사까지다. 이름표와
  행동 표지, 수첩, 버튼은 산세리프 그대로다. 전자책도 본문만 명조고 UI는
  고딕이다.
- **굵기는 400 하나.** 그래서 서술 속 대사의 `font-weight: 700` 을 400 으로
  내렸다 — 소설에서 대사는 굵지 않고, 구분은 색(`#1f4e4a`)과 큰따옴표가
  이미 하고 있다. `font-synthesis-weight: none` 으로 가짜 굵게도 막았다.
  명조에 합성 볼드가 걸리면 획이 뭉개진다.
- **425 KB 를 한 번 받는다.** Google Fonts 링크였다면 사건 하나에
  0.7~1.2 MB 다(실측). `public/fonts/` 에 있으므로 Worker 스크립트 크기와는
  무관하다.
- `font-display: swap` — 받는 동안 산세리프로 먼저 읽히고 바뀐다.

**확인하는 법:** 눈으로는 안 된다. 한글 명조는 저대비라 작은 크기에서 고딕과
구별이 잘 안 가고, 실제로 이 세션에서 **멀쩡한 폰트를 안 먹었다고 잘못
판단한 적이 있다.** 라틴 글자를 크게 찍어 보면 한눈에 갈린다(`Hamburgefons`).
또는 같은 문자열의 폭을 재서 기본 서체와 다른지 본다.

### 건드릴 때 알아야 할 것

- 전부 `.chat-pane.scene` 아래에 있고 CSS는 `app/offline/offline.css` 맨 아래
  한 블록이다. `app/globals.css`는 **한 줄도 안 건드렸다** — AI 화면은 그대로다.
- **`scene` 클래스는 스프레드시트 위장일 때 붙지 않는다**(`OfflineDetectiveApp`
  의 `effectiveSpreadsheetTheme`). 그쪽은 한 줄이 한 행인 표여야 하는데, 장면
  로그 규칙이 (0,3,0) 이상이라 위장 규칙 (0,2,0)을 전부 덮어써 버린다.
  `:not()` 을 겹쳐 쓰는 것보다 JSX에서 빼는 쪽이 읽기 쉽다. 위장 테마에서는
  문장 단위 분리도 그대로 살아 있다.
- `.messages`의 직계 자식은 여전히 `.message` 하나씩이다. 턴을 `<div>`로 묶고
  싶어지더라도 **묶지 말 것** — 위장 테마의 행 번호(`::before` + `counter`)가
  직계 자식을 세므로 래퍼가 하나 끼면 격자가 통째로 어긋난다(globals.css 3447행
  주석이 같은 것을 경고한다). 묶는 대신 인접 선택자(`+`)로 간격을 준다.
- `.message-column`에 `width: 100%`만 주고 `align-items`는 건드리지 않았다.
  `stretch`로 바꾸면 그 아래 붙는 획득·제시 칩까지 폭 전체로 늘어난다.

## 검증하는 법

```bash
# 1. 전 사건이 메뉴만으로 완주 가능한지 (오프라인 엔진을 고쳤으면 반드시)
node --experimental-strip-types scripts/offline-playthrough-check.mjs

# 2. 타입·포맷·린트
npx tsc --noEmit
npx oxfmt --check app/offline/ app/gm/offline-*.ts
npx oxlint app/offline/ app/gm/offline-*.ts

# 3. 실제로 띄워 보기
npm run build          # ← vinext build를 직접 부르면 안 된다 (아래 함정 참고)
npx wrangler dev --port 8787
# http://localhost:8787/offline
```

1번은 모든 방에 들어가고, 모든 현장 행동을 소진하고, 모든 인물과 대화하고,
모든 질문을 하고, 가진 카드를 전원에게 제시하는 것을 14회 반복하는 완전
탐색이다. 모델이 없으니 **메뉴에 실제로 뜬 버튼만으로 마지막 모순 단계까지
갈 수 있어야** 사건이 성립한다 — 그것을 세는 것이 이 검사다.

## 함정 (한 번씩 다 밟았다)

1. **`npm run build`를 써라.** `vinext build`를 직접 부르면
   `scripts/build-case-assets.mjs`가 안 돌아서 **사건 목록이 조용히 0건이
   된다.** HTTP 200에 "검색 결과가 없습니다"만 뜨므로 알아채기 어렵다.
2. **코드 삭제에 여러 줄 정규식을 쓰지 마라.** `.*?`가 줄을 넘어가 멀쩡한
   블록을 통째로 지운 적이 있다(`tsc`가 TS1128로 겨우 잡았다). 정확한
   문자열 치환 + 등장 횟수 1 확인으로만 고친다.
3. **`localStorage`를 `useState` 초기값에서 읽지 마라.** React #418 하이드레이션
   불일치가 난다. `useEffect`로 옮긴다.
4. **한국어 조사를 템플릿에 박지 마라.** `{place}로`는 "사무실로"는 맞지만
   "레인 구역로"가 된다. `fill()`의 `{topic}`/`{object}`/`{placeDirection}`
   같은 형태를 쓴다. 완주 검사가 `은(는)` 잔재와 미치환 `{...}`를 잡는다.
5. **그리디 시뮬레이터 결과를 신호로 읽지 마라.** 탐색 순서가 절대 턴 수에
   묶여 있어서, 엔진을 안 고치고 이동 순서만 한 턴 밀어도 25건이 나가고
   29건이 들어온다. 믿을 것은 위의 완전 탐색(311/311)이다.

## 남은 일

- **사용자 실플레이 대기.** 그 피드백이 다음 작업을 정한다.
- **두 사람이 말하지 않는 턴이 아직 많다.** 장면 로그는 「같은 턴에 나온 두 줄이
  서로에게 하는 말로 읽히게」 하는 데까지다. 실제 플레이 12턴을 덤프해 보면
  탐정·한지우 중 아무도 말하지 않는 턴이 절반을 넘고(쿨다운 2턴 + 대사 자리가
  붙는 행동이 한정적), 같은 한지우 한마디가 12턴 안에 두 번 나오기도 한다.
  화면이 아니라 `offline-engine.ts`의 대사 풀·`offline-session.ts`의 쿨다운
  문제이므로, 실플레이에서 여전히 허전하면 거기를 본다.
- 부르기 인원을 한 명에서 늘릴지는 실플레이 뒤 판단(한 줄 변경).
- 수첩에 main의 `진술`/`메모` 탭을 옮겨 올지 — 제안만 하고 보류 중.
- CASE305 마스터의 `S-CH04-01`/`F-CH04-01` 내용 중복 — 사건 작성 쪽 문제라 보고만 했다.
- 진행률의 `증거 n/m`과 수첩 바닥 `확보한 단서 n/m`의 분모가 다르다(14 대 13).
  main에서도 그렇고 이 브랜치가 만든 것이 아니다. 스프레드시트 상태 표시줄의
  '합계:' 칸을 비워 둔 이유가 이것이다.
