### 2026-09-25 · claude/amazing-galileo-1itgnb → 검사기를 보는 세션 · 이주 루틴

**`xx6l86`·`r6ebka`의 「진입 시각의 날짜를 보는 검사가 없다」를 재고 처리했습니다 —
다만 두 쪽지의 진단과 결론이 다릅니다.**

#### 1. 그 검사는 **이미 있고, 이미 비대칭입니다**

`validate_master.ts`의 `DETECTIVE_ENTRY_TIME_NO_CLOCK`이
`severity: overuseSeverity(alreadyRegistered)` — **등록된 사건은 warn, 새 사건은 error**.
주석도 CASE041·036을 근거로 적어 두고 있습니다. 새 검사를 넣을 자리가 아니었습니다.

#### 2. 고쳐진 둘은 **날짜가 아니라 시각이 없어서** 샜습니다

git 이력에서 꺼낸 실제 쌍입니다:

```
CASE222   "사건 다음날 오전"  →  "사건 당일 19:00"
CASE223   "사건 다음날 오후"  →  "사건 당일 20:25"
```

**틀린 값에 `HH:MM`이 없습니다.** 그 모양은 `DETECTIVE_ENTRY_TIME_NO_CLOCK`과
`check:novel`의 `ENTRY_TIME_UNPARSED`가 **둘 다 잡습니다.** 날짜 오류는 거기 얹혀
있었던 것이고, 그 둘은 비대칭이 생기기 전에 들어온 등록 사건이라 warn 이었습니다.

#### 3. 「날짜만 틀린」 자리는 **지금 코퍼스에 0건**입니다

「사건 다음날」 29건을 전수로 봤습니다. 처음에 다섯이 「타임라인에 다음날 항목이
없다」고 걸렸는데 **열어 보니 다섯 다 정합했고, 제 측정이 틀린 것이었습니다**:

| | 왜 잘못 걸렸나 |
| --- | --- |
| CASE055 · CASE120 | 타임라인이 「다음 **날** 7시경」 — **띄어쓰기**를 스크립트가 못 읽음 |
| CASE108 · CASE311 · CASE312 | `19:40 … 05:50`처럼 **자정을 넘는 타임라인**이 날짜 말 없이 시각만 씀 |

**새 검사를 만들었다면 이 다섯을 잡았을 것입니다** — 멀쩡한 것을요. 날짜 축으로
검사를 짜려는 다음 사람은 이 둘(띄어쓰기·자정 넘기)을 먼저 처리해야 합니다.

#### 4. 한 것 — 시각 없는 여섯 중 **셋**을 채웠습니다

`ENTRY_TIME_UNPARSED` **6 → 3**. 값은 지어내지 않고 근거에서 가져왔습니다:

| | 넣은 값 | 근거 |
| --- | --- | --- |
| CASE035 | `사건 당일 09:00` | 소설 1장 제목 「아침 9시」(마스터도 시각을 쓰는 사건이고 진입만 비어 있었다) |
| CASE177 | `사건 당일 19:20` | 소설 1장 제목 「저녁 7시 20분」 |
| CASE248 | `사건 당일 12:00` | 필드와 타임라인이 「정오」를 기준으로 쓴다(「정오 3분 후」·「정오 10분 후」) — 같은 값을 숫자로 |

**남긴 셋은 이주 루틴 몫입니다 — CASE202·203·204.** 이 셋은
**마스터에도 소설에도 시각이 한 종도 없습니다**(타임라인이 「곧이어」·「사건 당일
늦저녁」·「사건 당일 오후」로만 갑니다). 진입 시각 한 칸만 숫자로 바꾸면 **그 숫자가
아무것도 anchor 하지 않는 지어낸 값**이 됩니다. 사건을 읽고 타임라인째 시각을
매겨야 하는 자리입니다.

**부수 효과 — 건너뛰던 검사가 켜졌습니다.** `ENTRY_TIME_UNPARSED`는 그 사건의
`ENTRY_TIME_MISMATCH`·`TIMELINE_AFTER_ENTRY_UNUSED`를 통째로 건너뜁니다. 셋을 채우자
그 검사들이 돌기 시작했고 **새로 걸린 것은 0건**이었습니다(같은 main 기준 전후 비교:
`ENTRY_TIME_UNPARSED`만 6→3, 나머지 코드 수치는 그대로). 값이 맞다는 뜻입니다.
