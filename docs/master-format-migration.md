# 기존 마스터를 현재 스키마로 올리는 작업

코퍼스 308건 중 39건만 지금의 마스터 스키마에 부합한다. 나머지를 한 번에 몇 건씩 올린다.

지금 상태는 `npm run audit:format`이 말해 준다. `--list`를 붙이면 사건 id까지 나온다.

```
마스터 308건 — 부합 39건, 미달 269건
  NO_RELATIONSHIPS   269건
  PROSE_STAGE_KEY     73건   (전부 관계도 같이 없음)
```

**걸리는 항목은 둘뿐이다.** 진입 시각과 raw_text 파싱은 308건 전부 통과한다.

## 왜 스크립트로 못 하나

`relationships`는 인물·동기와 맞물린 내용이어야 한다. `private_strain`이 비었거나 `public_face`와 같은 말이면 검사기가 반려한다. 사건마다 그 사건을 읽고 써야 하는 일이라, 269건 × 3개 = 800개 넘는 관계를 사람(또는 모델)이 실제로 쓴다.

## 한 번에 5건

번호가 낮은 것부터. `npm run audit:format --list`의 `NO_RELATIONSHIPS` 목록에서 앞에서 5건을 집는다.

**그 목록이 비면 두 번째 단계로 넘어간다.** 같은 검사가 「관계는 있는데 모양이 나쁜 사건」을 따로 세어 준다 — `RELATIONSHIPS_CULPRIT_HUB`(전부 범인에게 붙음)와 `RELATIONSHIPS_ORPHAN_CHARACTER`(빠진 인물 있음). 거기서 앞에서 5건을 집어 **관계를 더하거나 바꿔** 두 조건을 채운다. 이미 있는 관계를 지우지는 말고, 모자란 쪽을 보탠다.

### 각 사건에서 하는 일

**1. 먼저 읽는다.** `data/pending-cases/<ID>/<ID>.master.json`과, 있으면 `<ID>.source.md`. 소스에는 그 사건이 원래 무슨 이야기였는지가 산문으로 있다 — 관계를 지어내지 말고 거기서 끌어낸다.

**2. `relationships`를 쓴다.** 최소 3개, 서로 다른 인물 쌍. 그리고 **양쪽 모두**:

- **범인이 낀 관계가 적어도 하나** — 없으면 동기가 허공에 뜬다.
- **범인이 안 낀 관계도 적어도 하나** — 이건 바닥이 아니라 짝이다. 처음 20건에서 10건이 관계를 전부 범인에게 붙여 별 모양이 됐는데, 그러면 이 필드를 넣은 이유가 반쯤 죽는다. 진범 말고는 아무도 무게가 없으면 플레이어가 추리할 것이 없다. 범인과 무관한 두 사람 사이에도 걸린 것이 있어야, 그 사람을 의심할 이유와 의심을 풀 이유가 둘 다 생긴다.
- **등장인물 전원이 적어도 하나의 관계에 나온다** — 어느 관계에도 없는 사람은 이름과 역할만 있는 배경이 되고, 탐정이 그에게 물어볼 것이 없다.

| 필드 | 무엇 |
|---|---|
| `id` | `R01`, `R02`… |
| `between` | 인물 id 둘. `key_figures`의 피해자(V##)도 올 수 있다 — 범인과 피해자 사이가 사건의 심장인 경우가 많다 |
| `nature` | 둘이 어떤 사이인가 |
| `public_face` | 누구에게 물어도 나오는 겉모습 |
| `private_strain` | 인물이 **먼저 꺼내지 않는 것**. 빚, 숨겨 주는 것, 최근에 틀어진 일 |
| `surfaces_when` | 탐정이 무엇을 건드렸을 때 그것이 새어 나오는가 |

`full_truth.motive`와 `actual_timeline`, 각 인물의 `knowledge_limits`·`red_herrings`가 재료다. **이미 마스터에 암시적으로 들어 있는 관계를 명시적으로 옮겨 적는 것이지, 새 사실을 만드는 것이 아니다.** 사건의 진상이 바뀌면 안 된다.

**3. 단계 키가 서술문이면 같이 고친다.** `contradiction_stages`의 `from_stage`/`to_stage`가 한글 문장이면 짧은 상태 키로 바꾼다.

- 첫 단계의 `from_stage`는 반드시 문자열 `initial`
- 각 단계의 `to_stage`가 다음 단계의 `from_stage`와 **글자 그대로** 같아야 한다
- 그 단계에서 무엇을 인정하는지가 드러나는 이름으로. `stage_1`/`stage_2`는 쓰지 않는다 — 검사는 통과하지만 GM이 지금 어느 단계인지 이해하는 데 아무 도움이 안 된다. 예: `initial` → `admits_lending_key` → `admits_presence`
- `case_complete.required_established_facts`나 다른 곳이 옛 키를 참조하고 있으면 같이 바꾼다

**4. 그 밖에는 아무것도 건드리지 않는다.** 서술을 다듬거나 증거를 더하거나 인물을 고치지 않는다. 이 작업은 빠진 필드를 채우는 것이지 사건을 다시 쓰는 것이 아니다.

## 검증

사건마다 `npm run check:case <ID>`를 돌린다. **종료 코드가 0이 아니면 그 사건은 커밋하지 않는다.**

- 이미 registry에 올라간 사건이므로 코퍼스 중복 검사는 warn으로 내려온다. 그건 이 작업의 대상이 아니다.
- 새 **error**가 생겼으면 그건 내가 넣은 관계가 깨졌다는 뜻이다 — 인물 id 오타, 같은 쌍 중복, `private_strain`이 비었거나 `public_face`와 같은 말.
- **`RELATIONSHIPS_CULPRIT_HUB`와 `RELATIONSHIPS_ORPHAN_CHARACTER`는 warn으로 나오지만, 이번에 내가 만진 사건에서는 0이어야 한다.** 이미 머지된 사건에서 error가 되면 실플레이 피드백 작업 흐름이 막히므로 warn으로 두었을 뿐이고, 지금 쓰고 있는 관계에 대해서는 통과 조건이다. 뜨면 고친다.
- 다섯 건을 다 고친 뒤 `npm run audit:format`을 돌려 부합 건수가 5 늘었는지 확인한다.

## 마무리

한 실행이 한 PR이다. 제목은 `마스터 5건을 현재 스키마로 (CASE0NN~CASE0NN)`. 본문에는 사건별로 **무엇을 근거로 그 관계를 적었는지** 한 줄씩 — 나중에 실플레이에서 이상하면 되짚을 자리가 있어야 한다.

`npm run check:case`가 다섯 건 모두 통과했고 PR 검사가 초록이면 머지한다. 하나라도 3회 수정 후에도 실패하면 **그 사건만 빼고** 나머지를 올리고, 뺀 사건은 마지막 에러 목록과 함께 이슈로 남긴다.

`audit:format`이 미달 0건을 보고하면 이 루틴은 할 일이 없다 — 아무것도 하지 않고 끝낸다.
