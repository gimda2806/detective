# 기존 마스터를 현재 스키마로 올리는 작업

코퍼스 308건 중 39건만 지금의 마스터 스키마에 부합한다. 나머지를 한 번에 몇 건씩 올린다.

지금 상태는 `npm run audit:format`이 말해 준다. `--list`를 붙이면 사건 id까지 나온다.

```
마스터 308건 — 부합 39건, 미달 269건
  NO_RELATIONSHIPS   269건
  PROSE_STAGE_KEY     73건   (전부 관계도 같이 없음)
```

**걸리는 항목은 둘뿐이다.** 진입 시각과 raw_text 파싱은 308건 전부 통과한다.

## 왜 스크립트로 못 하나

`relationships`는 인물·동기와 맞물린 내용이어야 한다. `private_strain`이 비었거나 `public_face`와 같은 말이면 검사기가 반려한다. 사건마다 그 사건을 읽고 써야 하는 일이라, 269건 × 3개 = 800개 넘는 관계를 사람(또는 모델)이 실제로 쓴다.

## 한 번에 5건

번호가 낮은 것부터. `npm run audit:format --list`의 `NO_RELATIONSHIPS` 목록에서 앞에서 5건을 집는다.

**그 목록이 비면 두 번째 단계로 넘어간다.** 같은 검사가 「관계는 있는데 모양이 나쁜 사건」을 따로 세어 준다 — `RELATIONSHIPS_CULPRIT_HUB`(전부 범인에게 붙음)와 `RELATIONSHIPS_ORPHAN_CHARACTER`(빠진 인물 있음). 거기서 앞에서 5건을 집어 **관계를 더하거나 바꿔** 두 조건을 채운다. 이미 있는 관계를 지우지는 말고, 모자란 쪽을 보탠다.

### 각 사건에서 하는 일

**1. 먼저 읽는다.** `data/pending-cases/<ID>/<ID>.master.json`과, 있으면 `<ID>.source.md`. 소스에는 그 사건이 원래 무슨 이야기였는지가 산문으로 있다 — 관계를 지어내지 말고 거기서 끌어낸다.

**2. `relationships`를 쓴다.** 최소 3개, 서로 다른 인물 쌍.

**`says`를 같이 쓴다(2026-09 추가).** 관계마다 그 사이를 **그 사람 입으로** 말한 한 마디를 인물별로 적는 자리다. 면담할 수 있는 인물(CH##)은 빠짐없이, 피해자(V##)는 말할 수 없으니 생략한다. 없으면 런타임이 `nature`+`public_face`를 그대로 읽는데, 그건 「…업무 관계로만 알려져 있다」 같은 3인칭 설명문이라 인물이 아니라 해설자의 목소리로 읽히고, **짝에 적힌 값이라 양쪽이 글자 하나 안 틀리고 같은 말을 한다.** CASE290 실플레이에서 서지완과 임소민이 서로에 대해 같은 문장을 말했다. 이 필드는 관계 질문과 「○○이 어떤 사람이었는지」 질문 양쪽에서 쓰인다.

```json
"says": {
  "CH03": "\"원장님은 제 추천서를 써 주셔야 하는 분이었어요. 그 이상도, 그 이하도 아닙니다.\"",
  "CH02": "\"15년입니다. 야간은 제가 돌린다고들 하시는데, 원장님이 계셔서 돌아간 거죠.\""
}
```

양쪽을 다 쓸 때 두 값이 같으면 검사기가 `RELATIONSHIPS_SAYS_BROKEN`으로 반려한다 — 갈라 쓰는 이유가 그것이다. 말투는 그 인물의 `voice_profile`을 따르고, 탐정에게 하는 말이므로 존댓말이며 따옴표를 포함해 쓴다. 밀린 양은 `npm run audit:format`의 `RELATIONSHIPS_NO_SAYS`가 센다.

**중심은 피해자다.** 이게 이 작업에서 가장 틀리기 쉬운 지점이다.

처음 20건에서 루틴이 관계를 전부 범인에게 붙였다 — 범인 연결이 평균 3.05, 피해자가 1.70이었다. 원래 있던 39건은 정반대로 피해자 2.90, 범인 2.13이다. 사람이 쓰면 자연히 피해자 중심이 되는데 기계가 뒤집었다.

뒤집히면 두 가지가 무너진다.

- **관계도 모양만 보고 범인이 짚인다.** 가장 많이 연결된 사람이 답이다. 이건 데이터 모양 자체가 흘리는 것이라 런타임이 가릴 수도 없다.
- **수상해 보여야 할 사람이 아무하고도 얽히지 않는다.** 여러 사람이 저마다 피해자와 걸린 것이 있어야 저마다 동기처럼 보이고, 그래야 플레이어가 가릴 것이 생긴다. 범인 하나만 무거우면 추리할 것이 없다.

그래서 지켜야 할 것:

- **피해자가 낀 관계 수 ≥ 범인이 낀 관계 수.** 검사기가 이걸 잰다(`RELATIONSHIPS_CULPRIT_HUB`).
- **범인이 낀 관계가 적어도 하나** — 없으면 동기가 허공에 뜬다.
- **등장인물 전원이 적어도 하나의 관계에 나온다**(`RELATIONSHIPS_ORPHAN_CHARACTER`) — 어느 관계에도 없는 사람은 이름과 역할만 있는 배경이 되고, 탐정이 그에게 물어볼 것이 없다.

범인이 아닌 인물과 피해자 사이에 무엇을 적을지는 `red_herrings`가 이미 갖고 있다. 그 인물이 왜 잠깐 수상해 보이는지(`surface_suspicion`)가 곧 그와 피해자 사이에 걸린 것이다.

**`how_to_clear` 를 카드 제시로 풀리게 고친다(2026-09 사용자 결정 — 루틴이 맡는다).** 목표 상태는 **레드헤링이 오직 카드 제시로만 풀리는 것**이다. 그러려면 모든 `how_to_clear` 가 **주인공 본인 것이 아닌 증거 카드(`E##`)를 하나는** 불러야 한다. 밀린 양 273개는 `npm run audit:format` 이 센다:

| 코드 | 개수 | 할 일 |
|---|---|---|
| `HERRING_CLEAR_NO_ID` | 194 | 문장이 「A 와 B 를 대조한다」라고 말하는 그 A·B 의 id 를 적는다. 그중 하나는 남의 카드여야 한다. 대조할 카드가 정말 없으면 그 사람을 풀어 줄 물증·증언을 `evidence` 로 하나 만든다 — 다른 인물이 그 사실을 아는 형태(`○○에게 …를 묻는다`)가 가장 싸다 |
| `HERRING_CLEAR_SELF_ONLY` | 74 | 부르는 게 전부 본인의 말이다. 남의 카드를 하나 부른다(없으면 만든다) |
| 남의 진술만 부르는 5개 | 5 | `docs/herring-fact-only.md` 「남의 진술이 낌」 — 그 진술을 카드로 만든다 |

사건별 목록: `docs/herring-audit.md`(검사기 메시지 그대로), `docs/herring-no-evidence.md`, `docs/herring-fact-only.md`. **한 배치에 5건씩**, 관계 채우는 김에 같이 본다 — 두 번 읽지 않아도 된다. 고친 뒤 `npm run check:case <ID>` 로 세 검사를 다 돌린다(같은 방 카드끼리 명사가 겹치면 유출 오탐이 난다 — CASE101 이 그랬다).

장소 관찰 사실(`F-L##-OBS-##`)만 부르던 77개 중 76개는 이미 스크립트로 카드로 옮겨 뒀다(`scripts/promote-observation-to-card.mjs`). **그 카드 76개의 이름이 「<장소>에서 본 것」 임시 이름이다** — `docs/herring-card-names-to-review.md` 를 보고 지나가는 김에 이름을 지어 주면 된다. CASE101 하나는 새 카드 문장이 같은 방 E02 와 겹쳐 옮기지 못했다 — 문장을 갈라 쓰고 스크립트를 `CASE101` 만 지정해 돌리면 된다.

**본보기 — 첫 배치 5건(CASE008·015·016·018·023, 8개).** 사건을 다시 쓰지 않았다. 문장이 이미 「A 와 B 를 대조한다」라고 말하고 있어서, **A·B 에 해당하는 카드 id 를 붙이고 그중 하나가 남의 카드가 되게** 했을 뿐이다. 세 가지 꼴이 전부였다:

- 본인 카드만 부르던 것 → **같은 시각을 찍은 남의 카드**를 대조 상대로 붙인다. CASE008 R01: 서준혁 본인의 체크인 진술(E07)에 로비 보안 카메라(E03)를 붙였다 — 21시 25분 복도에 있던 건 강태민이다.
- 남의 목격담이 있는데 id 가 없던 것 → 그 카드 id 를 적는다. CASE023 R02: 「뒷골목 관찰 사실 및 다른 목격담」이 최윤슬(E05)·하진우(E04)였다.
- 대조 상대가 「범인을 가리키는 카드」인 것 → 그대로 쓴다. CASE015 R01: 도현우를 푸는 건 고재원의 목격담(E08)이 램프실에서 나온 사람을 서도협으로 가리키는 것이다. 레드헤링을 푸는 카드가 곧 진범 쪽 단서인 경우는 흔하고, 그게 맞다.

붙인 뒤 `check:case` 세 검사와, 그 카드를 주인공에게 제시하면 실제로 풀리는지 한 번 돌려 볼 것. 두 카드를 부르면 둘 다 내밀어야 풀린다(CASE023 R02 는 E05 뒤에 E04 를 내밀어야 도장이 찍혔다).

이 밀린 양이 0 이 되면 런타임을 「제시로만」으로 바꾸고(지금은 다시 말을 걸어도 풀린다) 검사기를 「남의 **카드**」로 좁힌다. 그 전에 바꾸면 273개가 못 푸는 상태가 된다.

**같은 김에 `how_to_clear` 를 본다(2026-09 추가).** `npm run audit:format` 의 `HERRING_CLEAR_NO_ID`(194건)·`HERRING_CLEAR_SELF_ONLY`(74건)가 그 밀린 양이다. 앞의 것은 문장에 id 가 하나도 없어 런타임이 「다 물어봤나」로 떨어지는 것이고, 뒤의 것은 부르는 게 전부 본인의 말이라 「본인이 아니라고 했다」로 풀리는 것이다. 사건을 다시 쓰는 일이 아니다 — 문장은 대체로 「A 와 B 를 대조한다」라고 이미 적혀 있으므로, **A 와 B 에 해당하는 `E##`/`F-##`/`S-##` 를 문장 안에 적어 주면** 런타임이 실제로 그 대조를 요구한다. 남의 카드·남의 진술·장소 관찰 사실(`F-L##-OBS-##`) 중 하나는 반드시 들어가야 한다. 사건별 목록은 `docs/herring-audit.md`.

**5건이 같은 말을 하지 않게.** 한 번에 5건을 맡으면 앞 사건에서 쓴 문장 틀을 뒤 사건에 그대로 끼워 넣기 쉽다. CASE078~082가 그렇게 나왔다 — 배경만 사격장·골프장·요트 건조소·양식장·PCB 공장으로 갈렸고, 관계 5개의 **슬롯 구성도 문장 끝맺음도 다섯 건이 같았다**(`확신이 서기 전까지는 이를 먼저 꺼내지 않았다`, `그 이유는 스스로도 알지 못한 채 넘어갔다` 등이 각각 5건 전부에 있었다). 검사기는 한 사건 안만 보므로 이걸 잡지 못한다. 그러면 GM이 다섯 사건에서 같은 대사를 한다.

그래서:

- **관계 쌍 구성을 사건마다 다르게 짠다.** `범인↔피해자` + `나머지 전원↔피해자`가 유일한 답이 아니다. 발견자와 기록 담당 사이, 심사관과 대표 사이처럼 피해자가 끼지 않은 쌍도 사건의 재료에서 나온다. 피해자 연결 수만 범인 것 이상이면 된다.
- **그 사건에만 있는 물건과 시각을 문장에 넣는다.** "개인 수첩에 적어 뒀다", "캡처를 팀 채팅방에 올려 뒀다", "작업화에 수조 바닥 뻘이 묻었다" — `actual_timeline`의 `world_fact`가 이런 것을 이미 갖고 있다. 시각도 그렇다(`20시 40분 안전관제실에서`).
- **배치를 커밋하기 전에 다섯 건의 `private_strain`을 나란히 읽어 본다.** 주어와 명사만 바뀐 문장이 보이면 그건 다시 쓰라는 신호다.

| 필드 | 무엇 |
|---|---|
| `id` | `REL01`, `REL02`… |
| `between` | 인물 id 둘. `key_figures`의 피해자(V##)도 올 수 있다 — 범인과 피해자 사이가 사건의 심장인 경우가 많다 |
| `nature` | 둘이 어떤 사이인가 |
| `public_face` | 누구에게 물어도 나오는 겉모습 |
| `private_strain` | 인물이 **먼저 꺼내지 않는 것**. 빚, 숨겨 주는 것, 최근에 틀어진 일 |
| `surfaces_when` | 탐정이 무엇을 건드렸을 때 그것이 새어 나오는가. **그것의 id를 문장에 괄호로 병기한다** |

`private_strain`의 **주어는 감추고 있는 쪽 본인**으로 쓴다. 오프라인 GM은 그 문장에서 이름이 가장 앞에 나오는 인물에게만 이 말을 시키므로(`offline-engine.ts`의 `strainSubject`), 짝의 반대쪽이 주어면 남의 비밀을 엉뚱한 입으로 흘리게 되고 그래서 문이 아예 안 열린다.

`surfaces_when`에 id가 없으면 AI 경로는 문장을 그대로 모델에게 넘기지만 **오프라인 GM은 그 균열을 영원히 못 연다** — 규칙 엔진은 자연어로 "도달했는가"를 판정할 수 없어 `how_to_clear`와 똑같이 문장 안의 id만 읽는다. 밀린 양은 `npm run audit:format`의 세 코드가 센다:

- `RELATIONSHIPS_SURFACES_NO_ID` 274개 — 자연어뿐. 문장이 가리키는 것의 id를 괄호로 넣는다.
- `RELATIONSHIPS_SURFACES_UNKNOWN_ID` 30개 — `promote-observation-to-card.mjs`가 관찰 사실을 카드로 옮기면서 `how_to_clear`/`hidden_until`의 id만 갈아 끼우고 여기를 두고 간 자국이다. `F-L##-OBS-##`가 남아 있으면 그 관찰이 옮겨 간 카드의 새 `E##`로 바꾼다.
- `RELATIONSHIPS_STRAIN_NO_SUBJECT` 32개 — 주어가 짝 밖이다.

`full_truth.motive`와 `actual_timeline`, 각 인물의 `knowledge_limits`·`red_herrings`가 재료다. **이미 마스터에 암시적으로 들어 있는 관계를 명시적으로 옮겨 적는 것이지, 새 사실을 만드는 것이 아니다.** 사건의 진상이 바뀌면 안 된다.

**3. 단계 키가 서술문이면 같이 고친다.** `contradiction_stages`의 `from_stage`/`to_stage`가 한글 문장이면 짧은 상태 키로 바꾼다.

- 첫 단계의 `from_stage`는 반드시 문자열 `initial`
- 각 단계의 `to_stage`가 다음 단계의 `from_stage`와 **글자 그대로** 같아야 한다
- 그 단계에서 무엇을 인정하는지가 드러나는 이름으로. `stage_1`/`stage_2`는 쓰지 않는다 — 검사는 통과하지만 GM이 지금 어느 단계인지 이해하는 데 아무 도움이 안 된다. 예: `initial` → `admits_lending_key` → `admits_presence`
- `case_complete.required_established_facts`나 다른 곳이 옛 키를 참조하고 있으면 같이 바꾼다

**4. 진술이 한 번에 쏟아지는 인물을 사슬로 묶는다(2026-09 추가).** `npm run audit:format`의 `KNOWS_UNGATED_FLOOD`가 세는 71명(40건)이 여기 해당한다. 그 목록에 이번 다섯 건이 있으면 같이 고치고, 없으면 건너뛴다.

무엇이 문제인지부터: 오프라인 GM의 「그 밖에 이상한 점은 없었는지 묻는다」는 `hidden_until`에 안 걸린 `knows`를 **적힌 순서대로 하나씩** 내준다. 잠금이 하나도 없는 인물은 버튼을 세 번 누르면 아는 것이 바닥난다. CASE030 실플레이에서 채이든이 그랬다 — 첫 면담 한 번에 다섯 개가 연달아 나왔고, 그중에는 밖에서 잠글 수 없는 문도, 몇 시간 담겨 있어야 그렇게 되는 인화지도 있었다. 탐정이 아직 암실에 들어가 보지도 않았을 때다.

**두 칸짜리 자물쇠로 적는다.** `hidden_until` 항목 하나가 순서와 열쇠를 같이 쥔다.

- `release_trigger` — **앞 진술의 id**. 이것이 순서를 세운다. 사슬의 첫 칸은 그 인물의 `initial_claims` 첫 줄(`S-CH0N-01`)을 쓴다. 첫 면담에서 들으므로 만나기만 하면 열린다.
- `release_prerequisite` — **그것을 여는 열쇠**. 그 사람 앞에 내밀 카드(`E##`), 다른 데서 들어야 할 말(`F-CH##-##`/`S-CH##-##`), 깨야 할 단계(`C##`) 중 하나. 여기 쓴 `E##`는 「손에 넣었다」가 아니라 **「이 사람에게 제시했다」**는 뜻이다.

`knows` 맨 앞의 한둘은 잠그지 않고 남긴다 — 만나서 물으면 나오는 것이 하나도 없으면 그 사람은 첫 면담에서 벽이 된다.

CASE030 채이든이 지금 이렇게 되어 있다(시범):

```json
"hidden_until": [
  { "fact_or_claim_id": "F-CH04-05", "release_prerequisite": "E02", "release_trigger": "S-CH04-01" },
  { "fact_or_claim_id": "F-CH04-03", "release_prerequisite": "E10", "release_trigger": "S-CH04-01" },
  { "fact_or_claim_id": "F-CH04-04", "release_prerequisite": "E12", "release_trigger": "S-CH04-01" },
  { "fact_or_claim_id": "F-CH04-02", "release_prerequisite": "E11", "release_trigger": "S-CH04-01" }
]
```

열린 채 남은 것은 `F-CH04-01`(문을 열었을 때 본 것) 하나다. 나머지 넷은 암실·인화실에서 무엇을 가져와 그 앞에 놓느냐에 따라 하나씩 열린다 — 환풍기 스위치를 보고 오면 「그건 대표님이 정한 규칙이었어요」가, 공정 기록지를 보고 오면 「인화지가 새까맸어요」가 나온다. **방이 사람을 열고, 사람이 방을 연다.**

**열쇠는 이미 사건 안에 있는 것에서 고른다.** 그 진술이 무엇과 맞물리는지는 대개 `related_timeline`과 증거의 `proves`에 이미 적혀 있다. 새 카드를 만들지 않는다.

**헛다리 주인공에게는 조심한다.** 그 인물에게 **아직 못 들은 잠긴 진술이 하나라도 있으면 오프라인 GM은 의심이 짙어지는 박자(`suspicion_deepener`)를 열지 않는다**(`offline-engine.ts`의 `hasUnheardGatedKnowledge`). 그래서 `release_prerequisite`에 **그 헛다리의 `how_to_clear`가 부르는 카드를 쓰면 안 된다** — 그 카드를 내미는 순간 헛다리가 풀려 버려서, 짙어지는 박자가 영영 건너뛰어진다. 71명 중 48명이 헛다리 주인공이므로 여기가 이 작업의 실제 함정이다. 다른 카드를 열쇠로 고르거나, 그 인물은 열린 채로 둔다.

**5. 알리바이 아닌 첫마디를 하나는 준다(2026-09 추가).** `npm run audit:format`의 `CLAIMS_ALIBI_ONLY`가 세는 94명이다. 4번과 마찬가지로 이번 다섯 건에 있으면 같이 고치고, 없으면 건너뛴다.

오프라인 GM의 첫 면담은 `initial_interview_range` 안의 진술 중 **알리바이꼴이 아닌 것을 먼저** 말한다. 묻지도 않았는데 「그 시각엔 사무실에서 전표를 정리하느라 계속 자리에 있었어요」가 인사 다음 줄에 나오던 것을 막으려는 것이다 — 1,558명 중 335명이 그랬고 **그중 81명이 진범**이었다. 캐물어 끄집어내야 할 거짓말이 저절로 나온 셈이다.

그런데 그 사람의 진술이 **전부** 알리바이꼴이면 미룰 데가 없어 그대로 나온다. 남은 94명이 그 경우다.

**고치는 법: `initial_claims`에 한 줄을 더한다.** 시각도 자기 행적도 말하지 않는 한 줄이면 된다.

- 그때 자기가 하던 일 — 「그날은 마감 재고를 두 번 세야 했어요. 늘 그렇습니다.」
- 발견 당시 현장의 상태 — 「문을 열었을 때 냄새부터 이상했어요.」
- 피해자에 대한 인상 — 「대표님은 아랫사람한테 싫은 소리를 안 하시는 분이었어요.」
- 그날 이상하게 느낀 것 — 「그날따라 뒷문이 열려 있었던 게 좀 걸렸습니다.」

쓰고 나서 새 진술이 `initial_interview_range`에 들어가 있는지 확인한다 — 범위 밖이면 첫 면담이 읽지 않으므로 고친 것이 아니다. 이 한 줄이 그 인물의 `voice_profile`대로 들리면 그것만으로 첫 대면이 사람 소개가 된다.

**알리바이 자체는 지우지 않는다.** 「사건 당시 어디에 있었는지 묻는다」가 그 진술을 그대로 내주고, 그 보기는 한 번 쓸 때까지 메뉴에서 사라지지 않는다. 옮기는 것이 아니라 **앞에 한 줄을 놓는 것**이다.

**판정은 엔진과 같은 정규식을 쓴다**(`offline-engine.ts`의 `ALIBI_HINT`를 검사기가 그대로 import한다). 넓게 잡혀 있어서 「그날 특별히 마주친 일도 없었어요」 같은 부인도 알리바이로 센다 — 검사기가 걸면 그 문장이 실제로 첫마디로 나오는 것이 맞는지 보고, 아니면 걸리지 않는 한 줄을 새로 쓰는 쪽이 빠르다.

**6. 그 밖에는 아무것도 건드리지 않는다.** 서술을 다듬거나 증거를 더하거나 인물을 고치지 않는다. 이 작업은 빠진 필드를 채우는 것이지 사건을 다시 쓰는 것이 아니다.

## 검증

사건마다 `npm run check:case <ID>`를 돌린다. **종료 코드가 0이 아니면 그 사건은 커밋하지 않는다.**

- 이미 registry에 올라간 사건이므로 코퍼스 중복 검사는 warn으로 내려온다. 그건 이 작업의 대상이 아니다.
- 새 **error**가 생겼으면 그건 내가 넣은 관계가 깨졌다는 뜻이다 — 인물 id 오타, 같은 쌍 중복, `private_strain`이 비었거나 `public_face`와 같은 말.
- **`RELATIONSHIPS_CULPRIT_HUB`와 `RELATIONSHIPS_ORPHAN_CHARACTER`는 warn으로 나오지만, 이번에 내가 만진 사건에서는 0이어야 한다.** 이미 머지된 사건에서 error가 되면 실플레이 피드백 작업 흐름이 막히므로 warn으로 두었을 뿐이고, 지금 쓰고 있는 관계에 대해서는 통과 조건이다. 뜨면 고친다.
- **`KNOWS_UNGATED_FLOOD`와 `CLAIMS_ALIBI_ONLY`도 warn으로 나오지만 이번에 만진 사건에서는 0이어야 한다.** 위 4·5번을 했다면 사라져 있다.
- 사슬을 넣었으면 `npm run check:offline`을 한 번 돌린다. 잠긴 진술이 대립 단계의 `requires_heard_claim_ids`에 걸려 있으면 열쇠를 잘못 골랐을 때 그 사건이 못 깨는 사건이 되고, 이것 말고는 아무도 그걸 못 잡는다.
- 다섯 건을 다 고친 뒤 `npm run audit:format`을 돌려 부합 건수가 5 늘었는지 확인한다.

## 뼈대를 갈아 끼울 때 — `full_truth`만 고치면 절반이다

동기나 트릭을 바꾸는 작업이 섞여 들어오면 이것부터 본다(2026-09
`claude/determined-wright-anfsht`가 CASE020에서 값으로 확인한 것이다).

**같은 사실이 마스터의 다섯 자리에 흩어져 적혀 있다** — `full_truth` 말고도
`actual_timeline[].world_fact`, `detail_rules[].result`,
`contradiction_stages[].must_not_release`, `knowledge_limits`,
`case_complete.accusation_requirements`. CASE020은 `full_truth`만 새 동기로
바뀌고 나머지 넷이 옛 줄기를 그대로 들고 있었는데, **검사기는 그 다섯이 서로
다른 말을 해도 통과시킨다.** 교차참조 검증은 id가 가리키는 곳이 있는지만 보지
문장이 같은 이야기를 하는지는 보지 않기 때문이다.

**가장 싼 방법은 옛 줄기의 낱말로 `grep` 한 번**이다(CASE020에서는 「불륜」·
「협박」·「최후통첩」이었다). 바꾸기 전에 그 낱말들을 적어 두고, 바꾼 뒤 마스터
전체에서 한 번 찾는다. 남아 있으면 그 자리가 아직 옛 사건이다.

## 마무리

한 실행이 한 PR이다. 제목은 `마스터 5건을 현재 스키마로 (CASE0NN~CASE0NN)`. 본문에는 사건별로 **무엇을 근거로 그 관계를 적었는지** 한 줄씩 — 나중에 실플레이에서 이상하면 되짚을 자리가 있어야 한다.

`npm run check:case`가 다섯 건 모두 통과했고 PR 검사가 초록이면 머지한다. 하나라도 3회 수정 후에도 실패하면 **그 사건만 빼고** 나머지를 올리고, 뺀 사건은 마지막 에러 목록과 함께 이슈로 남긴다.

`audit:format`이 미달 0건을 보고하면 이 루틴은 할 일이 없다 — 아무것도 하지 않고 끝낸다.
